# Build strategy — S1 (remote build), M0 decision

## Chosen strategy: S1 — REMOTE BUILD (DEFAULT)

All UI work is done against an **installed official Zen build** with the
Browser Toolbox enabled (`devtools.chrome.enabled`,
`devtools.debugger.remote-enabled`), using the CSS live-editing guide and
packaging experiments as temporary Zen Mods. The real browser is compiled in
GitHub Actions; only the finished installer is downloaded locally.

Rationale:
- The machine has **7.1–8.0 GB free** disk; the 10 GB project cap is below
  Zen's documented 30 GB requirement. A default local build would fail and
  can wedge the machine.
- S2 (artifact build, 6–7 GB) would still consume nearly the entire disk and
  breach the 7 GB abort threshold before producing anything; S3 (local full
  build, 30 GB) is forbidden.
- S1 local footprint: repo + node_modules + installed Zen ≈ **2–3 GB**, well
  under the cap.

## Projected peak usage (S1)

| Phase | Local disk | Where the build happens |
|---|---|---|
| M0–M2 UI work (this milestone range) | ~0.3 GB repo + 0.4 GB installed Zen | Local edits only; CI builds |
| CI build (per run) | 0 GB local | GitHub runner / hosted builder; artifact downloaded after green |
| After artifact download + install | ~0.4 GB installed Zen | Local testing only |

Peak local usage ≈ **0.8 GB**, leaving ~6+ GB headroom against the 10 GB cap.

## Abort threshold

If free space drops below **1.5 GB**, stop immediately, report, and wait.
Checked with `df -h .` before and after every heavy step; logged in
`docs/build-log.md`.

## What is NOT done locally (per constraints)

- No `npm run init` (downloads + extracts Firefox source + bootstraps toolchains).
- No `npm run build` or `npm run build:ui` locally (build:ui is JS/CSS-only but still runs through the surfer/mach pipeline; reserved for CI).
- No `npm start` locally (requires a built `engine/`).
- Engine patch flow (`npm run export` / `npm run import`) only after CI is green and a build is authorized.
